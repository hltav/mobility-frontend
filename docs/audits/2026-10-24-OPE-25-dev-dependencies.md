# OPE-25 — Triagem das dependências de desenvolvimento — 24/10/2026

## Escopo e resultado

Branch feature/OPE-25-governanca-ci-protecao-branches. HEAD preservado em 88ca12c3bfb182e5644ccf5fec82a9f47285c5f5, com o commit anterior 4834c233b4bc84e722cdcd5dcc86b2412480f647. Nenhum commit foi reescrito ou criado nesta etapa; nenhuma publicação GitHub, PR, merge ou ativação de Ruleset. Os 23 arquivos retidos foram registrados por checksum e preservados. Backend, banco, fontes src, rotas, budgets e configuração PWA não foram modificados.

O audit completo inicial reportou 32 entradas: 2 baixas, 8 moderadas, 19 altas e 3 críticas. Após correções e npm ci: zero entradas em todas as severidades, tanto no audit de produção quanto no completo. Instalação, build, testes Angular, governança e lint passaram. Isso é o resultado da base de advisories consultada, não garantia universal de segurança ou prova de exploração anterior.

## Como interpretar o npm audit

São 32 entradas de pacote, não 32 CVEs nem 32 falhas independentes. Quatro entradas marcadas diretas são ferramentas de desenvolvimento (@angular/build, @angular/cli, postcss e vitest). As outras 28 são transitivas. Em três entradas (@angular/build, @angular/cli e express-rate-limit), via contém apenas outros pacotes, sem advisory próprio: são agrupamentos/metavulnerabilidades propagados pelo npm. Vitest combina advisory direto e propagação de mocker. A mesma URL de advisory pode aparecer em mais de uma entrada ou em faixas distintas de Undici 6 e 7. Contagem deduplicada por URL: 124 advisories.

A entrada zod vulnerável era a cópia 4.3.6 da cadeia CLI, não o Zod 4.6.7 de produção. A separação prod/dev decorre da alcançabilidade da dependência no lock; uma dependência marcada dev ainda executa no pipeline.

## Cadeias críticas e correções

### Piscina

Antes: frontend → @angular/build 21.2.9 → piscina 5.1.4.

Depois: frontend → @angular/build 21.2.28 → piscina 5.3.2, versão corrigida da linha 5. O [advisory crítico](https://github.com/advisories/GHSA-67c8-pqhq-4rmx) descreve gadget de execução de código em workers condicionado à poluição de protótipo. O [advisory anterior](https://github.com/advisories/GHSA-x9g3-xrwr-cwfg) não cobria todas as opções herdadas. Sem assumir que a aplicação oferece a primitiva de poluição, o risco é relevante: o builder usa Piscina em seu WorkerPool e transformações JavaScript durante build/teste. Corrigir a dependência evita depender dessa pré-condição permanecer ausente.

### Proxy-addr

Antes: frontend → @angular/cli 21.2.9 → @modelcontextprotocol/sdk 1.26.0 → express 5.2.1 → proxy-addr 2.0.7. Express-rate-limit compartilha Express por peer.

Depois: frontend → CLI 21.2.28 → SDK 1.32.1 → Express 5.2.1 → proxy-addr 2.0.8. O [advisory](https://github.com/advisories/GHSA-jqcg-44mw-7w3h) afeta confiança em proxies com determinadas configurações IPv4/IPv6, permitindo falsificação de IP. A falha depende de servidor/configuração de trust proxy afetados; não significa que o frontend estático hospede Express. SDK/servidor MCP são ferramentas do CLI, não Laravel. O workflow não inicia ng mcp; não foi validado servidor MCP ponta a ponta nem demonstrada exploração. Ainda assim, atualizar o transitivo protege esse uso e evita manter a falha no ambiente de desenvolvimento.

### Tar

Antes: frontend → CLI 21.2.9 → pacote 21.3.1 → tar 7.5.13. Há segunda aresta pacote → @npmcli/run-script 10.0.4 → node-gyp 12.3.0 → tar 7.5.13.

Depois: CLI 21.2.28 → pacote 21.5.1 → tar 7.5.22; a cadeia node-gyp 12.4.0 converge para a mesma versão. O [advisory crítico de descompressão](https://github.com/advisories/GHSA-23hp-3jrh-7fpw) tem correção em 7.5.19, mas outros advisories afetam até 7.5.20; 7.5.22 sai de todas as faixas reportadas. O parser/extrator processa arquivos que podem consumir CPU/disco ou provocar falhas. No projeto, entra nas ferramentas de obtenção de pacotes/compilação nativa do CLI; não é runtime do browser. O npm usado para instalar também tem bibliotecas próprias: este audit do projeto não atesta a versão de tar embutida no executável npm. Não foram executados payloads de exaustão ou exploração.

## Exposição durante build, testes, instalação e CI

- Build transforma CSS/JS, usa workers e pode ler source maps. Piscina, PostCSS, Babel, source-map-js, glob/brace-expansion e ferramentas de browser mapping têm contato com fontes/configuração do projeto, inclusive propostas por PR. Corrigir ferramentas protege o processo que gera os artefatos; não basta o audit do runtime do browser estar limpo.
- Testes usam Vitest/mocker/Vite com arquivos do repositório. Falhas de mock/servidor, paths e arquivos podem afetar o runner ou dados acessíveis ao processo. JSDOM/unidade não prova ausência de todas as condições dos advisories; os testes não precisam expor um servidor público para merecer correção.
- CLI contém capacidades opcionais MCP, rede e obtenção de pacotes. Os caminhos Express/proxy-addr e vários avisos Hono/SDK pressupõem uso de servidor, transporte ou middleware específico. O CI atual não chama MCP; isso reduz a exposição desse cenário, sem justificar ignorar o pacote. O código consultado do CLI usa SDK no comando mcp e pacote em package-metadata.
- Tar/pacote/node-gyp e bibliotecas de rede/autenticidade afetam a cadeia de ferramentas e processamento de entradas/arquivos. Não concluir que cada pacote instalado é executado por todo build. Não se atribuiu ao tar do projeto a extração feita pelo npm global.
- Código de PR já pode executar comandos durante install/testes. Audit não é sandbox nem verificação completa de supply chain; token mínimo, checkout sem credenciais persistidas, runner isolado e ausência de secrets em PRs continuam necessários. Não foram adicionadas credenciais nem permissões.

## Política Security avaliada e preparada

| Estratégia                              | Cobertura                                | Limitação                                                                                                         |
| --------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| npm audit --omit=dev --audit-level=high | Dependências alcançáveis em produção     | Antes passava mesmo com 32 entradas nas ferramentas; não protege sozinho o pipeline                               |
| npm audit --audit-level=high            | Runtime e ferramentas de desenvolvimento | Maior sensibilidade a alertas e disponibilidade da base de advisories; exige triagem e manutenção dos transitivos |

Recomendação adotada no patch local: manter os dois comandos em Security, com nomes de etapas explícitos e sem continue-on-error. Security consulta o lockfile sem executar npm ci ou scripts do PR. Install depende de Security; só após aprovação instala dependências e executa governança. Build/Angular tests/Lint continuam dependendo de Install. Assim alertas altos/críticos conhecidos podem bloquear antes da instalação, sem renomear o check requerido pelos Rulesets. Os resultados moderados/baixos continuam visíveis nos relatórios e devem ser triados; o threshold high não os transforma em ausência de vulnerabilidades.

O audit é temporal e depende do registry; indisponibilidade/erro também reprova, sem fallback para sucesso. Não houve adição de allowlist, supressão, redução de severidade ou remoção de verificações. A policy pull_request_target não foi alterada: apenas metadados, contents:read, sem checkout da origem, secrets ou execução de código do PR. Workflows/proteções só serão comprovados no GitHub após publicação autorizada e bootstrap; Rulesets continuam Disabled.

## Resolução, falhas e reprodutibilidade

A primeira tentativa de npm install apresentou falha interna edgesOut null ao tentar resolver peers opcionais; não foi contornada com force ou legacy-peer-deps. Uma resolução isolada com reaproveitamento parcial do lock deixou arestas requeridas ausentes: seu audit aparentemente limpo não foi aceito como prova e o arquivo não foi aplicado ao repositório.

A resolução final foi gerada do zero em outra cópia temporária. As dependências diretas não alvo foram temporariamente fixadas às versões já instaladas para não promover upgrades incidentais; as quatro atualizações e overrides foram avaliados antes da aplicação. Manifest final preserva as faixas originais das dependências não alvo e o lock registra as versões resolvidas pelo npm. Um npm ci real do projeto comprovou integridade/completude: 598 pacotes instalados, Husky prepare executado, audit completo sem vulnerabilidades. Nenhum checksum foi inventado e nenhum lock intermediário incompleto foi versionado.
